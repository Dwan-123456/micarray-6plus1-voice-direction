# L4-L6 可调分块伪实时链

本页描述 `1.3.5` 开发线的渐进式 L4-L6 预览。它不改变正式的 20 ms 审计链：
`L2 -> L3 -> L5(SKIPPED: offline_after_l4) -> ResultJoiner -> DecisionRecord` 仍按原
`WindowKey` 提交。渐进式结果是可替换的旁路预览；停止采集后，Hub 封存的完整轨仍会运行一次
权威 L4/L5/L6，并原子替换预览。

## 默认实验配置

- L1 IMCRA 预降噪关闭；CountNet 人数估计关闭；
- L2 使用 MUSIC，方向 ID 开启，IMCRA 噪声白化开启，DPD 关闭；
- L3 使用 DS；Hub 响度补偿关闭；
- L4 使用 MossFormer2，GPU 推理；
- L5 MarbleNet、DNSMOS 和 L6 CAMPPlus 使用 CPU；
- 渐进块长默认 10 秒，可配置为 3～15 秒的任意整数秒；重叠默认 1 秒。
- L2/L3/L5阶段队列默认各100窗（约2秒），L4-L6等待队列默认2块。

上游块长不要求是偶数。CAMPPlus 的 2 秒声纹片段有独立的连续缓存：例如 3 秒块末尾未满
2 秒的有效人声会保留并与下一块拼接，不丢弃，也不补成假语音。所有边界仍严格落在 20 ms
权威时间轴上。

## 数据流与调度

```text
Runtime启动后台预载MF2/DNSMOS/CAMPPlus
  -> 与首个音频块累计并行，不阻塞采集
L3 host 完成一个 20 ms hop
  -> 只发轻量 wakeup，不在 L3 线程拼大块或计算 SHA
  -> 独立 chunk producer 从 Hub claim 最多一个有界 admission round
  -> 后台队列接纳成功后才 ack/推进该 ID 游标
  -> L4 GPU：单人旁路；双人 MF2 + 1 s overlap + permutation repair
  -> L5 CPU：滚动上下文，只有不再受未来音频影响的帧进入预览
  -> L6 CPU：缓存 2 s 声纹证据，按节流周期发布可替换人物归并
  -> latest-only Test UI mailbox
```

队列满、模型失败或停机时，未被接纳的 Hub claim 不推进游标，因此同一音频区间可以精确重试。
Hub只在锁内冻结区间和hop引用；大块拼接、校验和SHA在锁外完成，避免阻塞20 ms L3写入。
L1-L3 不等待 L4-L6；预览失败只在状态栏显式报告，不能伪装成完整 final。停止阶段有有限超时；
若 GPU worker 仍未退出，就禁止启动会与它争用同一 GPU 的权威离线校正。

## L4 分块语义

单人轨直接 48 -> 16 kHz 旁路。双人轨的第一个完整块保留末尾 1 秒，只提交已经稳定的前缀；
后续推理输入为“上一块 1 秒输入尾 + 新块”。新旧输出重叠用于匿名声源换序判断，再经 1 秒
交叉淡化提交。`stable_branch_id` 只表示跨块连续身份；面向 L6 的 A/B 排名按累计匹配分重新计算，
不能把 branch 0 永久等同于候选 A。

人数采用 L2 方向数的单调 1 -> 2 路由。短历史可以在发现第二声源后重放并替换早期单人预览；
超出安全回放上限时必须标记预览降级，并把完整纠正留给停止后的权威作业，不能在 worker 内无界
同步重放整段录音。

## L5 与 L6 的渐进结果

MarbleNet 不是逐块无状态模型。渐进适配器在每条稳定 L4 分支上保留左右上下文，并延迟发布
仍受未来音频影响的右端帧；停止冲刷时才提交尾帧。L4 水位与 L5 稳定水位分别记录。

不同ID按各自稳定终点生成预览；错开出现或提前结束的轨道不得被最早结束ID的全局水位裁短。
单一水位只表示当前revision覆盖到的最大权威时间，逐轨水位同时写入元数据。

L6 预览维护跨块的 2 秒 CAMPPlus 证据缓存，并在本次会话内保留全部轻量embedding，复用未变化片段。为了避免每 3 秒都
对完整历史做一次二次方聚类，L6 只在首次、拓扑变化或固定时间间隔更新；其 speaker 编号和归并
在录音结束前都属于 provisional。停止后的完整离线 L6 才是最终人物结果。

## 资源与结果边界

- GPU 只常驻一个 MF2 预览模型；L3 默认在 CPU，禁止实时 L3 与 MF2 同时占用同一 CUDA 设备；
- CPU 承担 Hub 构块、L5、降频 DNSMOS、CAMPPlus 与 L6；这些工作不在采集线程或 Qt 线程执行；
- 渐进DNSMOS每30秒采一个9.02秒窗口，停止只补固定尾窗；完整分支精算留给canonical；
- MF2和CAMPPlus实例跨渐进与canonical复用，避免停止后重复加载模型；
- 后台队列和 latest-only UI 邮箱均有硬上限；状态公开提交数、处理数、队列深度、丢块和错误；
- 渐进结果不写入 `DecisionRecord`、RecordingStore 或 Catalog，不修改正式录音/数据 schema；
- Test UI 的临时 WAV 只是试听缓存。新 revision 可替换旧 preview；canonical 成功后迟到 preview
  不得再次覆盖界面。

## 性能验收

以音频库中的 `Pass-开始静音` 录音先完成端到端回放，再比较 3/5/8/10/15 秒块长。每组至少记录：

- 首个 L4、首个 L5、首个 L6 预览相对音频水位的延迟；
- MF2 单块耗时、整体 RTF、GPU 峰值分配/保留显存；
- CPU L5/DNSMOS/L6 分项耗时、队列高水位和 dropped blocks；
- L3 20 ms 节拍、丢窗率、停止冲刷耗时和最终 canonical 耗时；
- 输出时间轴连续性、分支换序、L5 边界和 2 秒声纹跨块余量。

默认 10 秒只是首个基线，不预设最优值。3 秒通常降低首帧等待但增加重叠、调度和 CPU 后处理
频率；15 秒相反。最终选择必须同时满足质量、稳定性、显存和 RTF 门禁。

基准脚本默认还运行停止后的canonical；`--progressive-only`只用于块长矩阵。脚本使用临时数据根，
不写正式`data/`，但不包含Qt刷新、Test UI试听WAV写入或真实麦克风回调负载，因此不能替代实机长时验收。
